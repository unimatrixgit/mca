# Existing politics and conquest integration

Repository baseline: 787ba3e2b527811bb57df2d0bbc8de54736ba654, 6 November 2026. This report describes source contracts at that revision. Installed JAR presence/version inventory is recorded separately by task 326; it does not establish parity of every political class. Implementation must first reconcile the actual artifacts and schema with this baseline.

## Current political authority

[Politics.java](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/Politics.java) implements five playable faction identifiers: Fremen, Harkonnen, Corrino, Atreides and Ordos. It stores votes, names, appointments, Trust funds and one invasion in YAML. With SharedDatabase configured, refresh/save use the shared SQL record; without it, politics.yml is local. Comments describing all state as local are therefore incomplete descriptions of the current source.

An Emperor or house leader is the current highest tally, with UUID ordering breaking ties. Election buckets are floor(epoch time / 604800 seconds), not ISO weeks or a staged nomination/voting/closed election. Candidates must be online at voting time. The election does not wait for a final count before exposing its current winner. Appointments are valid only while their Emperor and bucket match. These are existing rules, not the proposed succession or council system.

[DuneCore.java](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/DuneCore.java) constructs Politics and directly dispatches `/dune politics` and `/dune trust` to it. Politics.command performs synchronous refresh/save calls. Moving new work to a worker pool while still calling these methods would retain blocking SQL and would not satisfy the new main-thread requirement.

[SharedDatabase.java](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/SharedDatabase.java) defines existing dune_politics(id,yaml). MySQL save writes the whole blob and a dune_game_events(topic='politics') event in one transaction when the YAML changes. The update compares against the proposed new YAML, not an expected previous revision; it is not compare-and-swap protection for two servers independently reading and modifying that blob. Java synchronized only serializes one Politics instance. New concurrent invasion/election authority must not treat this as a transactional domain API.

## Existing invasion and money behaviour

Politics.command allows the current elected faction leader to invade another valid faction. Its default cost is 50000 from the shared Vaerkring Trust value, duration 60 minutes, and five distinct defender contributions can end the invasion. There is one attacker/defender/until record. There are no coordinates, territorial ownership, preparation schedule, occupation evidence, objective chain, victory-to-succession transaction or per-campaign escrow in this implementation.

The Trust is a YAML numeric value; its deposit branch calls Vault withdrawal separately from the subsequent YAML save. It is not a funded, double-entry imperial treasury. No design migration may silently equate that value with a clan bank or staff bank, or infer that an older deposit can be replayed safely.

[ClanStore.java](../../DuneClans/src/main/java/com/dunerealms/clans/ClanStore.java) has existing clan context and operation/stock ledgers. Its locked context procedure returns a website-linked UUID, clan ID, owner/officer/member role and versioned kit design. A CP clan owner is not automatically the elected leader of one of the five political factions.

[ClanMoneyStore.java](../../DuneClans/src/main/java/com/dunerealms/clans/ClanMoneyStore.java) has existing dune_clan_wallets and dune_clan_wallet_ledger, uses DECIMAL(20,2), and debits/credits dune_economy_balances on the same supplied SQL connection. It also defines a distinct network staff-bank wallet/ledger. Those methods are specific to clan transfers and kit fees. There is no verified generic invasion escrow, house treasury mandate or imperial budget API to call. The proposal must add that authority explicitly and preserve current receipts.

[PUBLIC-NAMES.json](../../docs/PUBLIC-NAMES.json) maps public planet/faction names and Solaris to dunemarks without changing internal identifiers. New public text should use the approved public names; point configuration and existing protocol keys must retain canonical IDs. Currency migration still needs a reconciliation decision for the legacy Trust; display-name mapping is not proof of a ledger conversion.

## Quest systems with different contracts

[QuestStore.java](../../DuneQuests/src/main/java/com/dunerealms/quests/QuestStore.java) defines existing dune_quest_definitions and dune_quest_events. Its implemented engine is worm-survival; claims select enabled worm-survival definitions with FOR UPDATE SKIP LOCKED, snapshot the definition and finish only preparing/assigned events. The current definition schema explicitly constrains reward_dunemarks to zero.

[DuneQuests.java](../../DuneQuests/src/main/java/com/dunerealms/quests/DuneQuests.java) runs the encounter producer on Arrakis, uses worker threads for SQL, and schedules Bukkit/entity work back on the main thread. It enforces the two-worm cap and does not pay currency on completion. This scheduling pattern is reusable; its worm spawning, eligibility rules, engine filter and event fields do not already implement capture objectives across five planets.

[quests.mjs](../../website/control-panel/quests.mjs) provides authenticated CP quest views/admin definition requests through the private server-control bridge. Browser callers cannot choose a different UUID. The contract advertises zero monetary rewards and no manual encounter test. Capture support requires new versioned engine/definition interfaces rather than disguising a point as a worm-survival quest.

[QuestDiscovery.java](../../DuneMenus/src/main/java/com/example/dunemenus/QuestDiscovery.java), [quest-rewards.mjs](../../website/control-panel/quest-rewards.mjs) and [quest-rewards-mysql.sql](../../website/control-panel/quest-rewards-mysql.sql) implement a separate fixed hidden discovery: imperial-portal-eye-ra-v1, authenticated proof, one first finder and a one-use 1,000-Dunemark claim. These are useful receipt/authorization patterns, not a generic repeatable invasion-reward API. Its fixed IDs, amount and ledger must stay intact. The kit quest arc is another distinct progression contract and must not be overwritten by conquest events.

[DuneNPC](../../DuneNPC/src/main/java/com/example/dunenpc/DuneNPC.java) owns another mission system through [Smugglers.java](../../DuneNPC/src/main/java/com/example/dunenpc/Smugglers.java): local YAML contracts for tagged spice/water, destination checks and a thirty-minute real-time expiry. Its delivery path saves contract completion, calls Vault payout, applies Politics.levy and removes cargo. This is not an atomic shared capture/reward service. Its mission narration may link to future objectives, but its file/Vault workflow must not be reused as conquest settlement. Existing smuggler cargo/contracts and payouts need a compatibility plan, not a reset.

[ArrakisWater.java](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/ArrakisWater.java), Smugglers and DuneCore also consume political appointment facts and/or write Trust levies. They belong in the migration inventory alongside explicit politics commands. Fencing only the vote/invasion command would leave legacy economic writers active. The [private quest bridge](../../network/server-control/quest_engine.py) is another existing zero-reward worm-definition consumer; adding an engine requires a reviewed extension there as well as in Java and CP.

## Website and office consumers

[Politics.websiteSnapshot](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/Politics.java) exports current office display names and appointments without ballot records/UUIDs. [DiscordWebFeed.java](../../DuneRealms-minecraft-only/src/main/java/com/example/dunerealms/DiscordWebFeed.java) publishes that snapshot as DUNE_DIPLOMACY parts. [feed-api.mjs](../../website/worker/feed-api.mjs) checks the configured publisher, bounded multipart payload and snapshot freshness; [diplomacy.js](../../website/web/diplomacy.js) displays current offices. This is a delayed display feed, not transactional permission or invasion authority. It cannot carry confidential strategy.

[political-offices.mjs](../../website/node/political-offices.mjs), [watch-political-offices.mjs](../../website/integrations/mybb/watch-political-offices.mjs) and [PoliticalRanks.java](../../DuneEss/src/main/java/com/example/duneess/PoliticalRanks.java) derive current political roles from the legacy bucket/tally/appointment format. The forum worker reads committed SQL events and maps verified site-game links. Its derived landsraad role includes office holders beyond faction leaders; it is not the proposed council electorate. A new term/succession model needs coordinated consumers and expiry handling, without granting website/staff administration from a political office.

[player_kits.py](../../network/server-control/player_kits.py) derives exact office/term strings from the same legacy state and defines dune_office_kit_definitions. [kit_commerce.py](../../network/server-control/kit_commerce.py) rechecks officeTerm for official/faction listings; [kit-studio.mjs](../../website/control-panel/kit-studio.mjs) exposes those publishing authorities. [OfficeGear.java](../../DuneItems/src/main/java/com/example/duneitems/OfficeGear.java) tags items by office, owner and exact term, records dune_office_kit_claims and audits wearing authority. These are direct succession dependencies. A source migration cannot simply replace the term string everywhere: preserve existing definitions, claims, completed purchases and the current term's identity, while preventing new sales/wearing under an expired office. A migration itself must not grant a second office-kit claim.

## Presentation and missing interfaces

[NativeMenus.java](../../gui-common/src/main/java/com/example/dunegui/NativeMenus.java) bridges to DuneMenus. The current DuneMenus source announces a graphical Java inventory navigator and explicitly disables its Java-dialog route, while Bedrock native forms remain. DialogScreen/DialogSupport exist in source, including a capability check, but their presence does not mean the active navigator already fulfils this assignment's native-Java-dialog requirement.

The conquest design therefore proposes a separately reviewed politics presentation path: native Java dialogs for supported clients, compatible Bedrock forms and text/status fallback when unavailable. It must not silently replace the approved general navigator, require a pack or treat form responses as authorization.

A search of the inspected game/CP source found no implemented CAPTURE_POINT/HOLD_POINT objective engine, PROVISIONAL_RULE state machine, dune_pol_* schema or legitimacy model. All such names in [DESIGN.md](DESIGN.md) are proposals. This change contains documentation only; no schema, API, command registration, game rule, balance or permission is installed.
